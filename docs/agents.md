# Agents and computers

## Your own agents

The sidebar's **Agents** filter lists your own agents: Markdown files (`<name>.md`, the Claude Code / infer format - frontmatter `name`, `description`, optional `model`, and the instructions as the body). Agents are read from `.infer/agents` and `.agents/agents` of the directory the app was launched from, then from `~/.infer/agents` and `~/.agents/agents` - the first match wins on a name, and a new agent is saved to `~/.infer/agents`.

**New agent** opens an editor for the name, role, description, face, model and instructions, plus what this desktop adds: the agent's **Computer** (`workspace` in the frontmatter), its **Project** (`project`), the **MCP servers** it uses (`mcpServers`, see [MCP servers](mcp.md)) and its **Email** inbox with the **Allowed recipients** that may write to it (`email` and `allowed_recipients`). In the frontmatter the editor manages `name`, `description`, `role`, `model` and `emoji`, plus `workspace`, the desktop-only `project`, `email` and `allowed_recipients`, and `mcpServers`. Every other key already in the file is kept as found. An agent that lists no server uses every MCP server of its computer. Every agent starts with a robot drawn from its name, and you can pick one of Microsoft's animated 3D Fluent emoji (downloaded beside the agent file) or your own GIF or picture. Saving drops you into a chat with that agent: its instructions become the chat's system prompt.

The **Role** is the agent's job title, a few words such as `tester` or `code reviewer`, at most 40 characters. It shows under the agent's name in the Agents filter, and after its name in a room, as `jeff (tester)`. For a new agent, **Start from role template** writes it with `infer agents create <name> --role <role>` from its role's template - `tester`, `reviewer`, `writer` and `researcher` have one of their own, every other role starts from the default - and the editor goes on from the template's description and instructions. The description, face, model and computer already filled in carry over. A model the agent's file pins that this computer's gateway does not serve - such as a mock model left from an example - reads **not served** on its row and in the editor's Model list, because a chat or subagent here cannot run it. Pick a served model there, or **Inherit the selected model**.

Any chat can change agents without leaving it: **Switch agent** in the bar above the composer lists your agents with the current one checked, and picking one hands the chat to that agent from your next message. The conversation stays, so the agent picks up where the chat is. Its instructions apply from then on, and it may call only the tools its file allows - a call to any other tool is refused without an approval card. A running turn finishes as the agent it started with. A chat on another computer than the agent's moves to the agent's computer first, which waits for a running turn to end. **Main agent** at the top of the menu takes the chat's agent away, so the CLI's default `main` agent answers from your next message and the chat stays on its computer. Before the first message the picked agent simply opens the chat in the current project. Every chat is told the inbox of each agent that has one, so a switched chat still knows which inbox is its own. The CLI's own `main` agent file, which `infer init` may seed into `~/.infer/agents`, is not listed as an agent - it is the **Main agent** row.

Agents in `~/.infer/agents` can also hand work to each other through the CLI's `Agent` tool, so one agent's instructions can tell it to consult another by name. A chat with an agent can also message another agent - ask the researcher to send the tester a message, for example. The tester then starts a chat of its own on its computer, listed under the tester in the **Agents** filter, which opens on the researcher's message as a **Message from researcher** card. The tester's reply comes back to the researcher's chat the same way, and the researcher's next message continues the tester's chat. Messaging another agent needs the CLI daemon, which the desktop runs.

## A2A agents

An A2A agent is a service of its own that a chat delegates to over the [Agent-to-Agent protocol](https://a2a-protocol.org). A Markdown agent is who the chat is - its instructions become the chat's system prompt and it works with the chat's own tools and computer. An A2A agent is someone the chat asks: it runs somewhere else with its own model and tools, takes a task, and sends back the result, while the chat keeps its own agent and model.

**Settings > Agents** lists them below your Markdown agents and manages them through the CLI's `infer agents` commands:

- **Local A2A Agents (containers)** lists the ready-made agents of the [inference-gateway/agents](https://github.com/inference-gateway/agents) catalog, each with its version, what it does and its skills. Ticking one adds it (`infer agents add <name>`) and the app runs it as a Docker container on this computer, so it needs Docker. An added agent shows a dropdown with the model it thinks with, and picking another one updates it (`infer agents update <name> --model <model>`). Unticking removes it.
- **Remote agents** adds an agent that already runs - hosted elsewhere or started by you - by its URL, such as `http://localhost:8085`: type it and press **Add**. The app does not start it, so it must answer at that URL. **Remove** on its row takes it out again.

Every chat is told the URL of each added agent and can hand it a task with the `A2A_SubmitTask` tool - name the agent or its URL in your prompt. Submitting a task asks for approval first in Standard mode, while `A2A_QueryAgent`, which only reads an agent's card, does not. A task the agent is still working on shows in the status bar with an `A2A` badge, and the bar's `A2A` count says how many of the added agents answer. The containers of the local agents start when the app does and stop when it quits.

See [examples/a2a-agent](../examples/a2a-agent) to add one agent and send it a task.

## A computer of their own

An agent can also get a computer of its own: add the compute under **Settings > Compute** - a Kubernetes cluster added with **New cluster** or found with **Detect clusters**, or the one on your machine with **Provision local cluster** - saved to `~/.infer/compute.yaml`. Then add a workspace under **Settings > Workspaces**, on one of those clusters or with its own connection, saved as a workspace of the `infer` daemon in `~/.infer/daemon.yaml`. Pick the workspace as the **Computer** in the agent's editor (`workspace` in the frontmatter) and every new chat with it is teleported there before its first run, so its computer use drives that machine, not yours.

**Computers** in the top bar shows the latest screen of each such chat side by side. **Take over** on a computer, or in its agent's chat, holds the agent and lets you drive that screen with your own mouse and keyboard - a login, a captcha, a dialog in its way - until **Hand back** lets the agent continue from what it sees.

**Settings > Workspaces** lists the machines each workspace has in its cluster, ready or not, and deletes any one of them - a machine that fails to boot shows there as not ready. The chat of a deleted machine starts a new one on its next message.

A chat that already started can move too: **Move to workspace** in its composer sends it to a workspace or brings it back to this computer, between turns.

A Kubernetes workspace sets the **CPU** and **memory** of its computers, each as a request and a limit, in Kubernetes quantities such as `500m`, `2` or `4Gi`. They are saved as the `resources` block of the workspace in `daemon.yaml` and need `infer` CLI v0.255.0 or newer. Empty fields leave the amounts to the cluster. A running computer keeps what it started with, and the next one gets the new values. The **Computers** view shows what each computer was given - its CPUs, its memory and its GPUs - and whether it is a sandbox, a pod of its own in a cluster, or a real system.

A workspace's **User data** is a cloud-init script each of its computers runs as root when it boots, before the agent starts, to install what the agents need. The local cluster's workspace runs the CLI's Ubuntu desktop image, `ghcr.io/inference-gateway/computer`, and its user data installs Firefox with the opentask extension for [browser use](browser-use.md#on-an-agents-computer). A computer boots to an empty desktop - the browser stays closed until an agent opens it for a task that needs the web.

See [examples/computer-use](../examples/computer-use) for three agents on Ubuntu desktops in a local Kubernetes cluster.
